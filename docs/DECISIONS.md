# 技术决策记录 — DECISIONS.md

> 记录决策、理由、备选方案与验证情况。未验证项明确标注。

## D-001 采用单机 Python + FastAPI 架构

- 决策：MVP 采用单机 Python + FastAPI，不强制微服务。
- 理由：媒体处理、模型编排、实时调度集中在单机；成熟易测，便于最小闭环。
- 备选：多服务拆分（复杂度高，MVP 不必要）。
- 验证情况：待 G1 骨架验证（NOT RUN）。

## D-002 统一毫秒时间轴

- 决策：内部时间轴整数毫秒，保留原始 PTS/time_base，区间 `[start_ms, end_ms)`。
- 理由：跨音频/视频/ASR/姿态/事件对齐的统一基准。
- 验证情况：待 G1 实现与测试（NOT RUN）。

## D-003 模型经适配器接入，Mock 先行

- 决策：TTS/口型/视频源/推流均通过适配器接入，先以 Mock 验证接口与状态机。
- 理由：不将未验证模型引入主链路；接口稳定后再接真实模型。
- 验证情况：待 G1 Mock 适配器（NOT RUN）。

## D-004 存储先用 SQLite

- 决策：原型阶段用 SQLite；需要多进程写入/并发时评估 PostgreSQL。
- 理由：单机、零运维、易测试。
- 验证情况：未接入（NOT RUN）。

## D-005 候选模型均未验证

- 决策：Wav2Lip / MuseTalk / ASR / Vidu S2 均为候选，接入前须核实许可证、商业用途、硬件要求、真实性能、费用与接口。
- 验证情况：未验证（NOT RUN）。

## D-006 动作衔接采用锚点兼容（非唯一首尾帧）

- 决策：以多锚点有向图 + 锚点兼容性保证无缝衔接，不以「所有动作回到同一帧」为约束。
- 理由：唯一首尾帧约束过强——降低动作多样性、扩散模型难做到像素级一致、产生冗余过渡动作。
- 备选：唯一首尾帧循环（简单但受限，弃用）。
- 验证情况：待 G3 图谱实现与路径测试（NOT RUN）。

## D-007 姿态数据化采用骨骼序列表示（非图片）

- 决策：长时间直播帧经姿态估计转骨骼序列张量 `R^{T×N×C}`，再编码为低维动作 embedding 供 AI 消费。
- 理由：数据量比像素图小几个数量级，支持一次消费 10 分钟级连续动作；业界成熟方向（ST-GCN/Transformer）。
- 备选：逐帧图片送入 VLM（token 爆炸、成本不可行，弃用）。
- 验证情况：待 G3 姿态数据化管线（NOT RUN）。

## D-008 远程视频生成定位为可选补充

- 决策：Vidu S2 等仅用于动作库缺失、低频、非实时的预生成，生成后入库再调度；不作实时主链路。
- 理由：FPS≠延迟；自回归流式生成有身份/服装/背景漂移；实时生成为重算力，与低算力目标冲突。
- 验证情况：Vidu S2 已核实为真实产品（720p、25–42 FPS、Start-End/Reference-to-Video），但接入与延迟未实测（NOT RUN）。

## D-009 话术-动作-商品对齐需真实数据驱动

- 决策：「什么话配什么动作」的语义映射由 ASR+姿态对齐的真实三元组构建，禁止 LLM 凭空编造。
- 理由：这是 AI 学直播技巧的核心，须可追溯、可验证。
- 验证情况：待 G3/G5 数据闭环（NOT RUN）。
