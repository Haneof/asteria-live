# 架构 — ARCHITECTURE.md

> 本文档描述实际架构。MVP 阶段采用单机、可测试的工程结构，不强制微服务。

## 1. 逻辑模块与职责

```
ASTERIA-FORGE      素材导入 → ASR → 姿态数据化 → 动作分段 → 锚点候选 → 资产生产与质量验证
ASTERIA-DIRECTOR   商品知识 → 话术模板 → 脚本时间线 → 动作语义映射 → 互动决策 → 复盘
ASTERIA-LIVE       状态机调度 → TTS → 口型 → 媒体合成 → 推流 → 监控 → 人工接管
```

公共能力：
- ASTERIA-GRAPH：多锚点有向动作图谱。
- ASTERIA-SYNC：时间戳对齐与缓冲策略。
- ASTERIA-ASSETS：资产存储与版本管理。
- ASTERIA-OBSERVE：结构化日志、指标与监控。

## 2. 当前工程结构（实际）

```
asteria/
  core/       共享类型（时间轴等）、配置、日志
  adapters/   TTS / 口型 / 视频源 / 推流 适配器（含 Mock）
  graph/      动作图谱
  server/     FastAPI 管理 API
tests/
scripts/
docs/
```

## 3. 依赖方向

- `core` 不依赖任何上层模块。
- `adapters`、`graph` 依赖 `core`。
- `server` 依赖 `adapters`、`graph`、`core`。
- 实时主链路不得强依赖远程生成服务。

## 4. 时间基准

- 内部统一整数毫秒，保留原始 PTS/time_base。
- 区间 `[start_ms, end_ms)`。
- 视频、音频、ASR、姿态、动作、脚本事件经 `timeline_id` 对齐。

## 5. 核心架构决策（2026-10-25 核对确认）

### 5.1 动作衔接：锚点兼容，而非唯一首尾帧

- 不以「所有动作回到同一帧」作为无缝衔接约束；以**锚点（anchor）兼容性**替代。
- 主锚点 A0 + 若干局部锚点；两动作出口锚点 == 入口锚点即视为可衔接。
- 强制唯一首尾帧的问题：动作多样性下降；扩散模型难以做到像素级首尾一致；过渡动作冗余。
- 每个正式可调度动作必须有**经过验证的安全回归路径**（回到 A0 或等价锚点）。

### 5.2 姿态数据化：骨骼动作表示，而非图片

- 长时间直播帧不直接交给 AI；先经姿态估计转成**骨骼序列张量** `X ∈ R^{T×N×C}`（T=帧数、N=关节点、C=坐标通道）。
- 用 ST-GCN / Transformer 编码为低维动作 embedding，支持 AI 一次消费 10 分钟级连续动作。
- 数据量比像素图小几个数量级，是 ASTERIA-FORGE 姿态数据化管线的核心（G3）。

### 5.3 远程视频生成：可选补充，非实时主链路

- Vidu S2 等远程生成仅用于**动作库缺失、低频、非实时**的预生成，生成后入库再进入调度。
- 不得作为实时直播主链路；理由：25–42 FPS 为稳态吞吐非响应延迟；自回归流式生成存在身份/服装/背景漂移；实时生成为重算力操作，与低算力目标冲突。
- 需单独实测 TTFF、打断恢复、参考图切换延迟（G7）。

### 5.4 话术-动作-商品对齐闭环（AI 学直播技巧的关键）

```
真人直播视频
  ├─ 音频 → ASR → 话术文本（带时间戳）
  ├─ 视频 → 姿态估计 → 骨骼序列（带时间戳）
  └─ 对齐 → (话术片段, 动作片段, 商品语境) 三元组
        → 构建「什么话配什么动作」语义映射
        → 编导按映射选动作
```

该映射必须由真实数据驱动，禁止 LLM 凭空编造对应关系。
